### FINDING 1 (2026-08-26) — REAL BUG, Windows CRLF in two provisioning scripts

**Symptom:** `02-rds.sh` died at subnet-group creation with
`InvalidParameterValue: The input isn't valid. Input can't contain control characters.`

**Root cause (proven with `od -c`, not inferred):** `aws.exe` writes **CRLF** on Windows. The
two capture styles in these scripts behave differently under MSYS bash:

- `V="$(aws ... --output text)"` → command substitution strips the CR. Hexdump of a real
  capture: `s g - 0 9 5 9 ...` with **no** trailing `\r`. This is why `01-security-groups.sh`
  ran clean and why the bug did not surface until script 02.
- `mapfile -t arr < <(aws ... --output text | tr '\t' '\n')` → process substitution does
  **not** strip it. Hexdump of the raw stream ends `4 e 4 9 8 \r \n`, so the CR lands on the
  **last array element** only. RDS then rejects it as a control character.

**Blast radius — two sites, found by grepping every `mapfile`/`read` in the six scripts:**

| Site | Failure mode |
|---|---|
| `02-rds.sh:96` subnet lookup | **Loud** — RDS rejects the control character (what we hit) |
| `06-budget.sh:41` budget-name lookup | **Silent, and worse** — trailing CR makes the later `--budget-name` lookup miss, which reads as "no such budget" and invites creating a duplicate alert |

(`02-rds.sh:94`'s `IFS=',' read -r -a` is safe — it parses a user-supplied env var, not AWS
output.)

**Fix applied:** `| tr -d '\r' |` inserted ahead of the tab-split in both pipelines, with a
comment at each site explaining the constraint (matching the files' existing convention of
documenting Windows gotchas, as they already do for `MSYS_NO_PATHCONV`).
