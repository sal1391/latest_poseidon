# Phase 13 — Personalization Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every user gets a personal system instruction and a versioned, typed memory document — both injected into every router/synthesis prompt — plus a durable, idle-triggered background worker that distills finished conversations into new memory versions, and a settings surface to review/edit/restore both.

**Architecture:** Three new RLS-scoped tables (`user_profile`, `user_memory`, `memory_outbox`) behind three new per-user stores mirroring `core/chat/history.py`'s established `Store`/`for_user(sub)` facade shape. `orchestrator.py`'s two `assemble_system` call sites (currently fed permanently-empty `_USER_INSTRUCTION`/`_MEMORY_DOC` module constants — Phase 6's own disclosed placeholder) get real per-turn lookups; every turn-completion site also touches (upserts) the calling conversation's outbox row in the same best-effort posture `RunLogWriter` already uses for its own writes. A new standalone worker process (`poseidon/scripts/memory_worker.py`, a genuinely new architectural shape for this codebase — every prior background job has been a one-shot CLI script, never a polling loop) claims idle outbox rows using the raw, privileged database connection (bypassing RLS by design, the same posture migrations and the synthetic-data seeder already use) and then does everything else — reading that user's conversation, writing their new memory version, marking their outbox row — through the normal per-user `rls_transaction` path, so only the cross-user "which conversations are idle" query ever operates outside RLS. New `/api/me/settings` and `/api/me/memory*` routes complete the loop to a new frontend settings surface reached from the already-stubbed `UserMenu`.

**Tech Stack:** Alembic (hand-written), SQLAlchemy Core via `rls_transaction`, FastAPI, `RoleClient`'s pre-existing `memory` role (Claude Sonnet, already configured — no new LLM plumbing), React/zustand/vitest/MSW, `FOR UPDATE SKIP LOCKED` for the worker's claim query.

- **Schema (doc 05 §5, verbatim DDL below — Task 1):**
  ```sql
  user_profile (
    user_sub text primary key,
    system_instruction text not null default '',
    updated_at timestamptz not null default now()
  );
  user_memory (
    user_sub text not null,
    version int not null,                    -- monotonic per user; current = max(version)
    entries jsonb not null,                   -- [{type, statement, source_conversation_id, at}]
    created_by text not null check (created_by in ('user','distiller')),
    created_at timestamptz not null default now(),
    primary key (user_sub, version)
  );
  memory_outbox (
    conversation_id uuid primary key references conversations(id) on delete cascade,
    user_sub text not null,
    last_turn_at timestamptz not null,
    status text not null default 'pending' check (status in ('pending','done','failed')),
    attempts int not null default 0,
    last_error jsonb,
    updated_at timestamptz not null default now()
  );
  ```

- **RLS — deliberate divergence from every precedent since migration 0005, verbatim doc 05 §7:** *"Admins have no path to another user's `messages`, `user_memory`, or `user_profile` — those tables are RLS-scoped with no admin policy, deliberately."* All three tables get `ENABLE`/`FORCE ROW LEVEL SECURITY` + the one owner policy (`user_sub = current_setting('app.user_sub', true)`, `USING`+`WITH CHECK`, the same predicate every RLS table in this codebase reuses verbatim) — and **no `poseidon_admin` policy, no `poseidon_admin` grant, on any of the three.** Do not copy migration 0005/0006's admin-policy block here; that omission is the point, not an oversight.
- **`poseidon_app` grants, one deliberate departure named per table:** `user_profile` — `SELECT, INSERT, UPDATE` (no DELETE; a row is upserted, never removed by the app). `user_memory` — `SELECT, INSERT, DELETE` (no UPDATE; versions are immutable once written — append-only). **DELETE is granted here, unlike every RLS table since migration 0005** (`message_feedback`/`turn_run`/`tool_calls`/`llm_calls` all deliberately withhold it for audit-integrity reasons) because version retention pruning (`memory_keep_versions`) is ordinary log-rotation housekeeping, not an accountability record — RLS still confines any DELETE to the row's own owner regardless of grant, so this is not a broader exposure than the INSERT/UPDATE grants already made everywhere else, just a different judgment call for a different kind of row. Name this reasoning in code, don't silently diverge. `memory_outbox` — `SELECT, INSERT, UPDATE` (no DELETE; removal is the `conversations` FK cascade, the same RI-bypasses-RLS mechanism `message_feedback` already relies on).
- **The worker's privilege model (read this before Task 4 — it is the one place this phase's RLS story gets subtle):** the outbox worker's cross-user "which conversations are idle" query is the ONLY operation in this entire phase that reads/writes `memory_outbox` outside a per-user `rls_transaction`. It runs on the raw, privileged engine connection (the same one migrations and `poseidon.scripts.seed_synthetic` already use directly, never through `poseidon_app`/`poseidon_admin`) — `FORCE ROW LEVEL SECURITY` does not restrict a true Postgres superuser or a role with `BYPASSRLS` (only the table owner, if it is neither, is caught by `FORCE`); this codebase's compose `DATABASE_URL` role has already been established elsewhere in this project as exactly such a privileged connection. **Task 1's implementer must verify this empirically against the actual running compose Postgres** (`SELECT rolsuper, rolbypassrls FROM pg_roles WHERE rolname = current_user` over the raw `DATABASE_URL`, no `rls_transaction` wrapper) and disclose the result in their report before Task 4 relies on it — if the compose role turns out NOT to bypass RLS, that is a load-bearing finding requiring escalation, not something to silently work around. Every OTHER operation the worker does after claiming a row (reading that user's conversation content, writing their new memory version, marking their own outbox row `done`/`failed`) goes through the normal `Store.for_user(that_row's_user_sub)` / `rls_transaction` path like every other per-user operation in this codebase — the privilege escalation is scoped to exactly the one query that structurally cannot be scoped to a single user.
- **`assemble_system`'s fixed order is already built and already tested (Phase 5/6, `core/llm/prompts.py:246`) — do not change its signature or the four-section format.** This phase's job is entirely upstream: replace `orchestrator.py:387-388`'s permanently-empty `_USER_INSTRUCTION = ""` / `_MEMORY_DOC = ""` module constants with real per-turn values fed into the two existing call sites (`run_turn(..., user_instruction=..., memory_doc=...)` at orchestrator.py:653-654, and `_router_prompt_provenance`'s duplicate render at orchestrator.py:1299-1301).

- **New Settings fields (Task 4):** `memory_idle_minutes: int = 30` (doc 05 §5's own stated default), `memory_max_attempts: int = 5` (this plan's own choice — the doc names the field but not a number; 5 matches this codebase's other small-retry-count conventions and is generous enough that a single transient LLM-call failure never fails a distillation permanently). `memory_max_chars` (8000) and `memory_keep_versions` (20) **already exist** in `Settings` (config.py:77-78) from an earlier phase's forward-scaffolding — use them, do not redeclare.
- **The outbox `touch()` write is best-effort, not literally atomic with the turn's other writes — a disclosed, deliberate departure from doc 05 §5's literal "same transaction as the turn" phrasing.** Every existing turn-completion write in `orchestrator.py` (`writer.finalize(...)`, `state.put(...)`) already opens and commits its own independent `rls_transaction` — there is no shared transaction to join today, and restructuring `HistoryStore`/`RunLogWriter` to share one is out of this phase's scope. `ConversationOutbox.touch()` follows the identical pattern (opens its own transaction), called immediately after `state.put(...)` at each of the four completion sites. The failure mode this accepts: if `touch()` itself fails independently of the turn's other writes, that one turn's idle-clock bump is lost, which at worst delays that conversation's next distillation by one turn — never a correctness or data-loss risk, the same best-effort posture `RunLogWriter`'s own docstring already claims for its four write methods ("never raises").
- **Memory entries are typed and attributed, never free text distilled from tool output.** `type` is closed: `preference | scope | fact | correction`. An entry is only admissible if it derives from something the user said or a choice the user confirmed in the conversation transcript — text returned by `research.web_research` or any other external tool must never become an entry, verbatim or paraphrased, even if the distillation prompt is given the full transcript including tool results. This is a prompt-design constraint enforced by instruction + review, not a mechanically checkable one in this phase — the distillation prompt (Task 4) must state it explicitly and a task-review reader should sanity-check a real distillation run against it.
- **Size cap enforcement lives at ONE point: `UserMemory.write_version`.** It renders the candidate entries to markdown (the exact renderer `render_markdown` also uses) and rejects with a typed exception if that render exceeds `settings.memory_max_chars` — never truncates silently. `render_markdown` (used at prompt-injection time) does no capping of its own; it trusts that anything already in the table passed the check at write time.
- **Version retention is enforced at write time too**, inside `write_version`, after the new version successfully inserts: delete versions older than the newest `memory_keep_versions` for that user (the DELETE grant named above exists for exactly this).
- **API routes (doc 05 §8 / doc 01 §9):** `GET/PUT /api/me/settings`, `GET/PUT /api/me/memory`, `GET /api/me/memory/versions`, plus one new endpoint doc 08's validation list requires and doc 01 §9 implies but doesn't name a route for — `POST /api/me/memory/versions/{version}/restore` (restoring must itself append a new `created_by='user'` version, preserving the append-only invariant; it must never rewrite history in place). ### Task 3: `/api/me/settings` + `/api/me/memory*` routes
